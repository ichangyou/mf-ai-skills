# 验证与证据

## 选择最小充分范围

开始实现前，为本次任务明确可观察的成功条件，例如“长标题换行后主操作仍可见”“大字体下表单不裁切”。
从项目文档、CI 和现有脚本确定构建与启动命令，不猜 scheme、bundle ID、模拟器或路由。
按本次改动选择下面相关项，不为一个图标强制跑完整应用回归。

| 改动 | 实际检查 | 能证明什么 |
|---|---|---|
| SwiftUI/UIKit 实现 | 项目构建及相关已有测试 | 编译与测试覆盖的逻辑 |
| 布局、文字、颜色 | 运行受影响页面，查看前后截图 | 所见状态下的视觉结果 |
| 导航、输入、按钮 | 实际操作主要路径 | 被操作路径的行为 |
| 无障碍语义 | 项目可用的检查工具或实际 VoiceOver | 实际检查过的语义和顺序 |
| icon/logo 文件 | 渲染源文件，查看缩小与单色预览 | 文件可渲染及所见视觉表现 |
| App icon 集成 | 构建并在模拟器或设备检查 | 目标环境中的实际图标 |

没有现成测试时，不为颜色和间距变化新增仅匹配实现文字的测试；有交互逻辑风险则使用相关行为测试。

## UI 检查步骤

1. 尽量在修改前保存受影响界面的参考截图。来不及保存时明确没有基线，不重建假的“之前”。
2. 在实际项目中构建、启动并到达目标页面；截图来自对应构建，不能拿 HTML mockup 代替。
3. 查看截图本身，检查层级、裁切、重叠、对齐、对比和图标。截图命令成功不等于视觉通过。
4. 依据改动选择明暗、大字体、小屏、长译文及相关页面状态。记录实际设备与配置。
5. 实际操作受影响控件；修复发现的问题，再检查同一范围。

有现成视觉回归 harness 时复用；不为了本次小改自动引入整套测试基础设施。
截图差异代表变化，不自动代表缺陷；逐项区分预期变化与意外变化。
不自动覆盖既有截图基线来消除失败。

## 缺少工具时

- 无 Xcode 或可运行项目：仍可读代码、给出设计与修改，原生构建和运行保持未验证。
- 有构建但无截图或图片查看能力：分别报告构建结果和未完成的视觉检查。
- 有截图但无法交互：只报告观察到的视觉状态，不声称导航、键盘和无障碍行为通过。
- 缺少生图工具：交付实际做出的矢量或文字方案，不把概念提示词描述成图片。
- 检查失败时保留失败结论和原因，优先修复本次引入的问题；环境问题也不能改写为成功。

## 简短交付记录

按任务规模在回复中提供：

- 变化和原因：具体页面、行为或图形。
- 位置：修改文件；采用图片、可编辑源文件和必要预览的项目内路径。
- 证据：实际命令及结果、截图或操作过的路径、使用的模拟器/设备和外观。
- 限制：未检查的状态、缺失的能力和仍需要用户决定的事项。

无需为每次微调创建独立报告文件。需要保留设计规范、截图或报告时使用目标项目既有目录；没有约定再选择清楚的项目内目录。
