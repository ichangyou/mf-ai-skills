# iOS 设计

为当前任务执行：读取真实上下文 → 比较方向 → 统一规范 → 实现 → 实际验证。
遵守目标项目的 AGENTS.md / CLAUDE.md 和现有技术栈；不把设计请求扩大成产品功能重写。

## 按任务读取

先从实际加载的本文件所在目录解析相对路径，只读当前任务需要的参考：

- 原生页面、组件、交互或视觉优化：[原生界面](references/native-ui.md)。
- App icon、界面图标或原创品牌 logo：[图标与标志](references/icon-logo.md)。独立 App icon 任务可优先使用已安装的 `mufeng-app-icon`；未安装时仍按本文件执行。
- 进入实现或交付前：[验证与证据](references/verification.md)。

同时涉及页面和品牌时，先统一品牌规范，再应用到请求范围内的界面。
已有方案或明确的局部修改可以直接实施，不为走流程强做多方案。

## 1. 读取真实上下文

先检查工作区状态和目标项目说明，再读取相关界面、相邻组件、主题、Asset Catalog 和已有测试。
确认用户目标、目标用户、任务范围、最低 iOS 版本、设备范围、语言与现有构建入口。
从已有项目和本次指令获取这些信息；只对会阻止正确实现的缺口提问。

找出当前界面的主要任务与主要操作，明确问题属于信息层级、交互、可读性还是品牌表达。
给关键判断附代码位置或截图依据；把无法由源码确认的视觉判断标为待运行验证。
没有源码时可以评审截图或做独立设计稿，但不声称已经完成原生集成。

## 2. 比较方向

方向未定且需要取舍时，给 2–3 个结构或交互上真正不同的候选；每个说明解决什么、保留什么、代价是什么。
能渲染时制作最小可视草图；只有文字时明确标注为概念，不能当作已展示的视觉方案。
不靠换颜色或圆角冒充不同方向；不为比较构建完整的多套 App。

用户已指定方向则沿用。允许自主选择时说明选择依据后继续；用户要求先选方案时，完成候选后等待选择。
对局部优化先执行明确改动，额外建议写在回复里，不顺手改其他页面。

## 3. 统一规范

优先使用项目现有语义颜色、文字样式、间距、组件和图标。
没有规范时，仅为当前范围定义足够的颜色角色、文字层级、间距、形状和交互状态。
简单修改直接复用现有结构，不为了记录几个值创建新设计系统框架。
需要跨页面共用时，在项目已有位置记录语义 token 与用途，再映射到 SwiftUI/UIKit。

系统字体和原生控件是有效的设计选择；不要套用网页字体禁用名单或默认品牌配色。
保留真实内容，不编造指标、价格、评价或品牌资产；缺失内容明确标注，避免进入正式界面。

## 4. 实现

按目标项目原有架构修改 SwiftUI/UIKit 和 Asset Catalog；先完成最小可运行范围。
HTML 可以用于方向比较，不能替代原生布局、交互和无障碍验证。
原创图形交付可编辑源文件；生图结果按图标参考完成后续检查，不能将位图重命名为 SVG。

所有采用或交付的图片必须存入目标项目。工具输出到会话目录时，先确认文件存在且非空，立即复制到明确的项目路径并验证副本，再引用或继续下一张。
不引入画布专用文件格式、宿主工具名、素材服务或品牌字体。工具调用只使用当前宿主真实提供且已知用法的能力。

## 5. 实际验证

按[验证与证据](references/verification.md)运行与改动相称的检查，修复发现的问题后复查。
构建成功、截图已生成、视觉已查看、交互已操作是不同结论，分开记录。
有条件时完成实际检查，不因已有静态检查通过而省略视觉检查。
缺少条件时交付可用成果并点名未验证项，不伪造通过记录。

## 交付

简要交代行为或视觉变化、关键取舍、改动路径、实际检查和剩余限制。
多方案维持稳定名称；后续修改先重读当前文件，保留用户或其他工具已做的编辑。
不自动修改截图基线，不因设计请求自行发布、上传或提交商店。
Git 提交与推送遵守项目和用户指令，本 skill 不另加固定策略。

## 两端能力

Codex 与 Claude Code 共用上述流程，不依赖平台专用变量或固定工具名。
用宿主实际提供的文件、终端和图片查看能力；原生自动化或生图不可用时如实降级。
可选使用已安装的视觉回归等专项 skill，但本 skill 不要求安装它们，也不自动创建其 harness。
