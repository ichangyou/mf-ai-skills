# 沐风·微信读书推文

从真实阅读痕迹中发现值得公开分享的思想，改写成克制、有个人判断、可以直接发布的中文推文。目标是延续用户的认知轨迹，不是总结一本书。

## 依赖与边界

- 先读取并遵守 `/Users/changyou/.agents/skills/weread-skills/SKILL.md`。调用某项微信读书能力前，再读取其中指定的能力文档。
- 只依据接口返回、历史文件和当前上下文。不得虚构用户经历、批注、出处、作者、原文或发布时间。
- 微信读书不可用时，明确说明缺少什么；可以处理用户提供的导出文件，但不要假装已读取账号数据。
- 默认只生成候选稿并写入本地历史，不自动发布到 X，也不把“已生成”标记为“已发布”。

## 本地历史

历史默认存放在 `~/.codex/mufeng-weread-x/history.jsonl`。使用：

```bash
python3 /Users/changyou/.agents/skills/mufeng-weread-x-writing/scripts/history.py init
python3 /Users/changyou/.agents/skills/mufeng-weread-x-writing/scripts/history.py recent --days 30
python3 /Users/changyou/.agents/skills/mufeng-weread-x-writing/scripts/history.py stats --days 30
```

如果用户指定了其他历史文件或目录，优先使用用户位置；可通过 `--history PATH` 传入。读写格式见 [references/memory-and-output.md](references/memory-and-output.md)。

## 执行流程

### 1. 读取历史

生成前必须读取：

1. 最近 7 天历史：核心观点相似即淘汰。
2. 最近 30 天历史：比较正文、观点指纹、素材、主题和表达结构。
3. 30 天前历史：允许重访大主题，但必须有新素材、新连接、新案例、观点修正或明显更深的理解。
4. 主题统计：在质量接近时，提高低频主题优先级，避免主题疲劳。

历史为空时正常继续，并在本轮完成后建立历史。不要声称做过历史去重。

### 2. 读取微信读书记录

不要只看最近一本书。按需组合以下数据：

- `/user/notebooks`：按文档分页获取笔记本概览。优先关注近期更新、想法/点评多、总笔记多的书。
- `/book/bookmarklist`：获取候选书的个人划线。
- `/review/list/mine`：获取候选书的个人想法、章节点评和书评；按文档分页。此项优先级最高。
- `/readdata/detail`：用月度或总体数据发现近期阅读、长期偏好和反复出现的书。
- `/shelf/sync`：补充最近阅读书籍及更新时间。

“最近 30 天”优先按内容自身的 `createTime` 判断。`/user/notebooks` 的 `sort` 只用于发现近期发生过笔记活动的书，不等于每条内容的创建时间。所有时间戳展示时遵守 `weread-skills` 的转换规则。

控制调用规模：先用概览筛出高信号书，再读取内容；信息已经足以产生高质量候选时停止扩张。目标是广度足够且可验证，不是穷举账号全部数据。

### 3. 建立候选素材卡

在内部为每个候选记录：

- 来源书籍和 `bookId`
- 素材类型：个人想法、个人评论、划线、重要段落、阅读行为或跨书连接
- 极短素材摘要；必要时保留一小段准确原文
- 用户自己的立场，以及它对原文的补充、冲突或延伸
- 可独立成立的洞察
- 主题、关键词、可能的表达结构

优先级从高到低：

1. 用户自己的批注、评论、延伸或修正
2. 多本书反复出现且能形成新连接的主题
3. 反直觉、可行动、可迁移的洞察
4. 有力量且来源可核验的短句、诗词或文学表达
5. 单纯划线

详细选材和评分标准见 [references/editorial-guide.md](references/editorial-guide.md)。

### 4. 评分与去重

内部按六项判断候选：Insight、Usefulness、Originality、Depth、Shareability、Personal relevance。每项 1–5 分，不需要向用户展示分数。

先提取“观点指纹”，即一句最短的核心结论，再与历史比较：

- 0–30%：可用。
- 30–50%：只有新信息明确时改写后保留。
- 50–70%：原则上淘汰。
- 70% 以上：淘汰。
- 最近 7 天只要核心观点明显相似，直接淘汰。

同时检查相同素材是否刚用过、同一主题是否过密、开头和句式结构是否连续重复。无法可靠量化时，做明确的语义判断，不伪造精确相似度数字。

### 5. 写成推文

默认流程：理解原意 → 结合个人批注 → 抽象为普遍洞察 → 用自然语言重写。除非原句本身不可替代，否则不要直接摘抄。引用只能短且准确，并注明可核验的作者或书名。

混合使用单一观点、微型思考、反思、方法、哲思、文学、跨书连接和有价值的问题。不要六条采用同一结构。

正文要求：

- 像长期阅读、独立思考的人写的，简洁而完整。
- 不鸡汤、不营销、不标题党，不强造金句。
- 不用“读完某书，我学到三点”等摘要模板。
- 避免“真正厉害的人都”“你一定要”以及高频的“不是……而是……”。
- 少用问号、感叹号和 emoji。
- 可以有个人判断，不能虚构个人经历。
- 长度适合 X 阅读；观点确实需要展开时才写长。

### 6. 最终检查

逐条确认：

1. 最近 7 天无相同核心观点。
2. 最近 30 天无高度相似观点或刚使用过的素材。
3. 来源真实，书名、作者、原文准确。
4. 没有连续依赖同一本书、同一主题、相同开头或相同句式。
5. 每条至少提供新观点、新角度、新连接、更深理解或值得保存的文字之美。
6. 正文脱离原书语境仍成立，并且不是对旧稿换词复述。

宁缺毋滥。最多输出 6 条；只有 3–4 条合格时就输出 3–4 条。

### 7. 输出、落盘并写入历史

严格使用 [references/memory-and-output.md](references/memory-and-output.md) 中的展示格式。指出“今日最值得发布的 2 条”，只给编号、主题和简短理由，不重复正文。

#### 落盘为 Markdown

终端输出之外，本轮结果必须另存一份 Markdown 文件。**统一通过 `scripts/save_output.py` 落盘，不要自己拼路径或用 Write 直接写文件**——目录判定、文件名递增和防覆盖都已固化在脚本里。

```bash
# 正文从标准输入传入，脚本负责加文件头并选路径
python3 /Users/changyou/.agents/skills/mufeng-weread-x-writing/scripts/save_output.py --count 6 < body.md

# 只想知道会落到哪里，不写文件
python3 /Users/changyou/.agents/skills/mufeng-weread-x-writing/scripts/save_output.py --dry-run
```

脚本回包为 JSON：`path` 是绝对路径，`dir_kind` 为 `project` 或 `root`，`written` 表示是否真的写了文件。终端那行「已保存到 …」直接用 `path`。

脚本实现的规则（说明用，不需要手工复刻）：

**目录判定**：默认取当前工作目录，也可用 `--cwd` 指定。

- 等于 `/` 或等于 `$HOME` → 视为根目录，写入 `~/Downloads/`。
- 其余任何目录一律视为项目目录 → 写入该目录。不要求目录里有 `.git`、`package.json` 之类的项目标志。

**文件名**：`weread-x-YYYY-MM-DD.md`，日期取本地当天。同一天重复运行时依次改为 `weread-x-YYYY-MM-DD-2.md`、`-3.md`，**不覆盖**任何已存在的文件。

**文件内容**：与终端展示的是同一份内容（编号正文 + 来源/主题/新鲜度/去重说明 + 今日最值得发布的 2 条），只在顶部多一个文件头。骨架见 [references/memory-and-output.md](references/memory-and-output.md) 的“Markdown 文件输出”一节。

**终端输出不变**：仍按展示格式打印全部正文，末尾补一行「已保存到 `<绝对路径>`」。

**写盘失败**时照常输出全文，并明确说明未保存及原因，不要静默跳过。

> 本条覆盖全局 CLAUDE.md 中“分析/规划文档默认存到 `~/Desktop`”的约定。本 skill 的产物按上面的目录判定走；用户本轮另行指定路径时，以用户指定的为准。

#### 写入历史

输出完成后，将本轮每条候选以 `status: generated` 追加到历史。保存正文、时间、观点指纹、主题、来源书籍、素材摘要、表达结构和关键词。若写入失败，仍可返回结果，但必须说明历史未保存，因此下一次无法保证跨会话去重。

历史文件路径与落盘的 Markdown 无关，始终按「本地历史」一节的规则处理，不随 `cwd` 变化。

不要把来源元信息混入推文正文。不要在历史中保存整章、长段原文或 API 原始回包。
